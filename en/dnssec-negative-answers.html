Understanding DNSSEC Negative Responses
Intervals in NSEC and NSEC3

When a query asks for a nonexistent name, DNSSEC returns more than a statement that the name does not exist: it also provides evidence that can be validated. To understand NSEC and NSEC3, which supply this evidence, it is important to distinguish the hierarchy of names from their ordering.

Key points: The name hierarchy describes which names are below which other names, and determines the Closest Encloser and Next Closer Name. Canonical ordering places names in a sequence and determines NSEC intervals. NSEC3 intervals instead use the ordering of hashes computed from names. Hierarchical depth and ordering are separate dimensions.

1. What does a negative response prove?

The two main kinds of DNS negative responses are NXDOMAIN, meaning the name itself does not exist, and NODATA, meaning the name exists but has no records of the requested type. Since signatures cover existing RRsets, DNSSEC does not sign an empty negative response itself. Instead, it signs NSEC/NSEC3 records that provide evidence of the existence or absence of names in the zone.

  • NSEC: Orders actual domain names canonically. A link from one name to the next shows that there are no names between them.
  • NSEC3: Hashes domain names and orders the hashes. A link from one hash to the next shows that there are no names represented by hashes between them.

2. The name hierarchy: adding labels

A domain name's hierarchy is followed from the rightmost label toward the left. The subdomain relationship can be shown as gov.example. → b.gov.example. → a.b.gov.example.. Thus, b.gov.example. is immediately below gov.example., and a.b.gov.example. is immediately below b.gov.example.. Adding a label on the left makes the name more specific. 

example.
└── gov.example.                 ← Existing name
    └── b.gov.example.           ← Does not exist
        └── a.b.gov.example.     ← Queried name (does not exist)

In this example, gov.example. is the deepest existing ancestor of the queried name: the Closest Encloser. The name one level below it that is also an ancestor of the queried name, b.gov.example., is the Next Closer Name. The Next Closer Name adds one label to the Closest Encloser; its position is determined by the hierarchy leading toward the queried name.

Conceptually, find the Closest Encloser by removing the leftmost label from the queried name repeatedly until an existing name is first encountered. This follows the name hierarchy: neither canonical ordering nor the relative values of hashes select the Closest Encloser.

3. Canonical ordering: arranging names in a sequence

DNS canonical ordering is a defined rule for comparing domain names. It is not about the direction in which text is read on a screen. Compare names starting at the rightmost label (closest to the root), moving left if the labels match. Within each label, compare characters (more precisely, octets) from left to right. Uppercase and lowercase letters are treated alike. If all compared labels match and one name ends, the name with fewer labels comes first.

Assuming only the following names exist, their canonical ordering is:

OrderDomain nameHow the comparison works
1example.There is no additional label beyond the common parent, so the shorter name comes first.
2a.example.Compare the label a to the left of example.
3b.example.Comparing the labels to the left of example, b comes after a in a.example..
4a.b.example.The labels on the right, b.example., match those of b.example.. That name ends here, so b.example., with fewer labels, comes first.
5ba.example.Compare the label to the left of example with that of b.example.. The label b is a prefix of ba, so the shorter label b comes first.
6z.example.The label z on the left comes after b.

In this ordering, b.example. (two labels) comes before a.b.example. (three labels). At the same time, a.b.example. is a child of b.example.. Parent-child relationships in the hierarchy and relative positions in canonical ordering convey different information.

4. NSEC intervals use canonical ordering

An NSEC resource record contains an Owner Name, a Next Domain Name, and Type Bit Maps. The Owner Name is the name at which the NSEC record resides and whose existence it demonstrates. The Next Domain Name is the next name in the zone in canonical order. The last name links back to the first, forming a circular chain of names in the zone.

FieldMeaning
Owner NameThe existing name to which this NSEC record belongs. The owner name itself demonstrates that the name exists.
Next Domain NameThe next existing name in canonical order after the Owner Name. It indicates that no other names in the zone lie between these two names. The interval excludes its endpoints.
Type Bit MapsA bitmap listing the record types present at the Owner Name. The absence of the queried type is used as evidence for NODATA.

The zone-file form is as follows (TTL and other details are omitted):

owner.example.  IN  NSEC  next.example.  A NS SOA RRSIG NSEC DNSKEY

Assume that only the names in the canonical-ordering table exist, with the following NSEC record:

ba.example.  IN  NSEC  z.example.  A RRSIG NSEC

The Owner Name, ba.example., exists, and no other registered name in the zone lies in the canonical-order interval before the next name, z.example.. This provides evidence that a queried name inside that interval, such as c.example., does not exist. If the Type Bit Maps include A, the Owner Name has an A record. Otherwise, subject to the other required conditions, the bitmap can be used to prove NODATA for an A query.

For NXDOMAIN, proving only that the queried name does not exist is not enough. The wildcard name immediately below the Closest Encloser must also be shown not to exist, demonstrating that no response was synthesized from a wildcard. NSEC therefore requires multiple proof components: evidence covering the queried name and evidence covering the wildcard name. If one NSEC record covers both names, that single record can supply both components. For NODATA at an existing name, the main evidence is that name's NSEC record and its Type Bit Maps.

5. NSEC3 orders hashes instead of names

NSEC3 hashes names and builds a chain ordered by hash values represented in Base32hex. Interval checks compare hashes computed with the same hash algorithm, salt, and iteration count, not the original domain names. Hash ordering does not reveal the original names' label counts or parent-child relationships.

NSEC3 also has an Owner Name, a Next Hashed Owner Name, and Type Bit Maps. The leftmost label of the Owner Name is the Base32hex-encoded hash of the original name. The Owner Name indicates that the name corresponding to this hash is represented in the NSEC3 chain. With Opt-Out, hashes of some delegations without DS records may be omitted, so not every name in the parent zone appears as an Owner Name. The Next Hashed Owner Name is the hash of the next name represented in the NSEC3 chain, in canonical hash order. The Type Bit Maps identify record types at the original name from which the Owner Name's hash was computed.

FieldMeaning
Owner Name<Base32hex-hash>.<zone-name>.. The leftmost label is the hash of a name represented in the NSEC3 chain, demonstrating that the name exists. Delegations without DS records omitted by Opt-Out may not appear as Owner Names.
Next Hashed Owner NameThe hash of the next name represented in the NSEC3 chain, in canonical hash order. No other hash on the chain lies between the Owner Name's hash and this next hash (although delegations without DS records omitted by Opt-Out may lie in this interval). The endpoints are excluded.
Type Bit MapsThe record types at the original name whose hash appears in the Owner Name. The absence of the queried type is used as evidence for NODATA.

The zone-file form is as follows (parameter details are omitted):

<Base32hex-hash>.example.  IN  NSEC3  1 0 0 - <next-hash>  A RRSIG

In addition to Type Bit Maps, an NSEC3 record contains a hash algorithm, flags, an iteration count, and a salt. In this simplified example, 1 0 0 - means SHA-1, no flags, zero iterations, and no salt, respectively.

Why Base32hex encoding preserves hash ordering

What is preserved is the order of the computed hash values, not the order of the original domain names. NSEC3 uses Base32hex-encoded hashes in owner names. The Base32hex alphabet is ordered by increasing value: 0 through 9, then A through V. NSEC3 owner names have the form <hash>.<zone-name>., with a common zone-name suffix within a zone. After comparing that suffix in DNS canonical order, comparing the hash labels from left to right gives the same order as comparing the unencoded hashes as byte sequences.

Base32hex characters5-bit valuesExample ordering
0 through 90 through 98 < 9 < A
A through V10 through 31A < B < ... < V

Base32hex maps the hash's bit sequence to characters in groups of five bits, starting at the beginning. At the first differing 5-bit group in two hashes, the corresponding characters have the same relative order as the group values. An NSEC3 SHA-1 hash has 160 bits, producing exactly 32 Base32hex characters. For example, an initial group of 01001 becomes 9, and 01010 becomes A. The fact that 9 precedes A matches the order of the original 5-bit values.

Hashing itself does not preserve DNS canonical name ordering. Hashing loses the relationship to the original order, but the subsequent Base32hex representation preserves the order among hash values. This is why the encoded hash in an NSEC3 owner name and the binary hash stored in Next Hashed Owner Name can be compared using the same ordering. 

Determined from the name hierarchy:
  Closest Encloser = gov.example.
  Next Closer Name = b.gov.example.

Checked using NSEC3 evidence:
  gov.example.       → Verify that its hash exists
  b.gov.example.     → Verify that its hash lies within an NSEC3 interval
  *.gov.example.     → Verify that the wildcard name does not exist

The following explanation using a matching Closest Encloser hash describes the basic case without Opt-Out. If Opt-Out omits that hash, use the closest ancestor whose existence can be proved with NSEC3, as explained in the next section.

In short, the Closest Encloser and Next Closer Name are determined from the name hierarchy. NSEC3 then checks that the Closest Encloser's hash exists and that the Next Closer Name's hash is covered by an NSEC3 interval. For NXDOMAIN, it also proves that the wildcard immediately below the Closest Encloser (*.gov.example. in this example) does not exist. The Next Closer Name is not found by hash ordering or by counting labels in a hash.

An NSEC3 NXDOMAIN proof therefore does not necessarily fit in a single record. It usually combines evidence that the Closest Encloser's hash is present, evidence covering the Next Closer Name's hash, and evidence covering the wildcard name's hash. These are multiple proof components; one NSEC3 record may serve multiple roles when its interval covers more than one required hash. For NODATA, the main evidence is usually the Type Bit Maps of an NSEC3 record matching the target name's hash.

6. Opt-Out: omitting delegations without DS records from the hash chain

A delegation with NS records but no DS record in the parent zone exists in that parent zone, but has no chain of trust from the parent to the child zone's DNSKEY. Even if the child publishes DNSKEY and RRSIG records, without a parent DS record its key cannot be authenticated through the parent's chain of trust. Validation therefore treats the child as "insecure", not "secure". Here, "delegation without a DS record" refers to the absence of a DS record in the parent, regardless of whether the child zone is actually signed. Ordinary NSEC3 includes the delegation name's hash in the chain. For large zones with many such delegations, Opt-Out allows those hashes to be omitted.

An omitted name's hash falls within an interval belonging to another name's NSEC3 record. The Opt-Out flag on that record indicates that the interval may contain delegations without DS records that are not represented in the chain. The flag belongs to the NSEC3 record covering the delegation name's hash, not to the delegation name itself.

If Opt-Out omits the actual Closest Encloser's hash from the chain, NSEC3 cannot directly prove that name's existence. Instead of the actual Closest Encloser, use the closest ancestor whose existence NSEC3 can prove: the Closest Provable Encloser. The Next Closer Name is then found by adding one label to the Closest Provable Encloser toward the queried name. RFC 5155 defines that the Closest Encloser and Closest Provable Encloser may differ in an Opt-Out zone. 

Parent-zone namespace and NSEC3 hash chain (schematic)

Parent zone:
  signed.example.       NS + DS   ← DS authenticates the child's DNSKEY; included in the hash chain
  child.example.        NS, no DS ← The parent cannot authenticate the child's DNSKEY; may be omitted by Opt-Out

Hash ordering:
  ... H(signed.example.)
       ───── Interval of an NSEC3 record with the Opt-Out flag ─────
       (H(child.example.) may fall here without appearing in the chain)
       → Next hash represented in the chain ...

The main fact this mechanism can validate is that a delegation has no DS record. A resolver can use an Opt-Out NSEC3 record covering the queried name's hash as evidence for a DS query and treat the delegation as "insecure", meaning it is not protected by DNSSEC. This is different from validating the child's DNSKEY or RRSIG and declaring it "secure": the proof of DS absence leads to an "insecure" validation state.

An Opt-Out interval may contain not only hashes of unsigned delegations, but also hashes of non-delegation names or nonexistent names. An Opt-Out interval alone therefore cannot prove that an arbitrary name does not exist (NXDOMAIN), or that every name in the interval must be an unsigned delegation. A proof of DS absence differs from the proofs of absence for the Next Closer Name and wildcard required in an ordinary NXDOMAIN proof.

In the unsigned.optout.mismatch examples on this site, the Next Hashed Owner Name of the Opt-Out NSEC3 record covering the existing delegation unsigned, which has no DS record, is changed to the hash of that delegation name. An NSEC3 record shows that the name corresponding to its Owner Name's hash exists, and Next Hashed Owner Name identifies the hash of the next name on the chain. Between them there are no hashes represented in the chain, except that Opt-Out may omit delegations. Thus, the interval from the Owner Name to Next Hashed Owner Name consists of the values strictly between the endpoints, not the endpoint names themselves. The endpoints represent names on the chain and are distinct from nonexistent names inside the interval. Here, setting the upper endpoint to the hash of unsigned makes that hash equal to the endpoint rather than inside the interval. The record can therefore no longer serve as evidence of DS absence for that delegation. The broken component is the proof interval, not the NSEC3 signature itself: the modified record has been re-signed.
