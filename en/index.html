DNSSEC Chain of Trust Test Page

This page provides test cases for validating the DNSSEC chain of trust.
Click "Open validator" to open the DNSSEC Delegation Validator.
In each table, "Chain of trust (+ denial-of-existence validation)" targets the zone apex (including NODATA proof validation if no A record exists there). "Full validation of the www name" targets the domain name prefixed with "www.". Domains for testing corrupted A-record signatures are listed in a separate table.

For an explanation of negative responses using NSEC/NSEC3, see Understanding DNSSEC Negative Responses.

Note: "Expected overall result" indicates the final result expected from the validator or a similar tool.
Note: Algorithm headings (RSASHA256, ED25519, etc.) refer to the signature algorithm used for the child zone's DNSKEY, A records, and other records, not the RRSIG algorithm used for the DS RRset in the parent zone (.jp).

The main labels in the domain names identify the following test cases.

Domain name labelsTest description
success A valid configuration in which DNSSEC validation succeeds.
keytag.ds.error
hash.ds.error		 The parent zone's DS and the child zone's DNSKEY have a mismatched Key Tag or Digest, respectively.
sign.ds.error
sign.dnskey.error
expire.dnskey.error		 A corrupted parent DS RRset signature, a corrupted child DNSKEY RRset signature, and an expired child DNSKEY RRset signature, respectively.
corrupted.sign.a.error The signature (RRSIG) covering the A RRset is corrupted.
missing.cover.mismatch The NSEC/NSEC3 interval does not cover the nonexistent name, so the denial-of-existence proof fails.
target.type.mismatch
target.type.mx.mismatch
target.type.txt.mismatch		 The NSEC/NSEC3 type bitmap contradicts the actual response, making the NODATA proof inconsistent. mx / txt indicate the query type.
unsigned.optout.mismatch The Opt-Out proof of DS absence fails for the unsigned delegation unsigned, which has no DS record.
iter0 / iter1
nosalt / saltA1B2		 The iteration count and salt used to compute NSEC3 hashes.
